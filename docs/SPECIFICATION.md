## 1. Design Document

### Decision Record

| Decision | Choice |
|---|---|
| **What** | Modern reimplementation of SCCS |
| **Target** | CLI tool, cross-platform (Windows, macOS, Linux) |
| **Language** | Java |
| **Build** | Gradle |
| **Dependencies** | Picocli (CLI args), SLF4J (logging), JUnit (testing) |
| **Project Layout** | Standard Gradle structure |
| **Package** | `com.sccs` |
| **Storage Format** | Full original SCCS `s.` file format |
| **Commands (v1)** | `get`, `delta`, `admin`, `prs` |
| **Delta Reconstruction** | Full reverse-delta (all `^AI`/`^AD`/`^AE` control records) |
| **Branched SIDs** | Supported |
| **Default `get` SID** | Most recent delta by timestamp |
| **Encryption (`^AY` flag)** | Supported |
| **Diff Engine** | In-house Java diff implementation (Myers or equivalent) |
| **Locking** | Advisory only |
| **Error Handling** | Graceful recovery with warnings (lenient mode) |
| **Test Fixtures** | Real `s.` files from historical UNIX archives |
| **API Shape** | Library (`SccsRepoConfig` handle) + CLI frontend |

### Functional Requirements

#### FR1 — `admin` command
- FR1.1: Initialize a new SCCS history file (`s.<file>`) in an `SCCS/` directory.
- FR1.2: Support initial file check-in with descriptive comment.
- FR1.3: Parse and write the full SCCS header format including checksum, delta table, and flags.

#### FR2 — `get` command
- FR2.1: Retrieve a specified SID from the SCCS history file.
- FR2.2: When no SID is specified, retrieve the most recent delta by timestamp.
- FR2.3: Reconstruct file content by applying reverse deltas (walking `^AI`/`^AD`/`^AE` control records).
- FR2.4: Support `-e` (edit mode) flag to check out a file with locking intent (advisory).
- FR2.5: Support retrieving trunk-only and branched SIDs.

#### FR3 — `delta` command
- FR3.1: Accept a modified file and create a new delta in the history file.
- FR3.2: Compute the difference between the current file and the previous version using an in-house diff algorithm.
- FR3.3: Store only the delta (change set), not the full file.
- FR3.4: Record metadata: timestamp, author, SID, and comment.
- FR3.5: Update the delta table, checksum, and body encoding.

#### FR4 — `prs` command
- FR4.1: Print the delta table (SID, date, author, comment) for a given SCCS file.
- FR4.2: Support filtering by specific SID or range.
- FR4.3: Print flags and other metadata stored in the history file.

#### FR5 — File format support
- FR5.1: Parse SCCS magic/checksum header line (`^Ah`).
- FR5.2: Parse delta table entries (`^As`, `^Ad`, `^Ac`, `^Ae`).
- FR5.3: Parse and honor SCCS flags (`^Af`), including the encryption flag (`y`).
- FR5.4: Encode and decode the file body, including `^A` byte-stuffing/escaping.
- FR5.5: Implement XOR-based encryption/decryption for bodies flagged with the `y` flag.

#### FR6 — Delta reconstruction
- FR6.1: Reconstruct any revision by starting from the full body (most recent) and applying reverse deltas.
- FR6.2: Correctly handle inserted lines (`^AI`) and deleted lines (`^AD`) marked by `^AE` terminators.
- FR6.3: Walk edit sequences in the correct order to produce a valid file.

### Non-Functional Requirements

#### NFR1 — Cross-platform compatibility
- NFR1.1: Must run on Windows, macOS, and Linux without platform-specific code (standard Java).
- NFR1.2: File path handling must use platform-independent separators.

#### NFR2 — Performance
- NFR2.1: Delta reconstruction for a file with 100 revisions must complete in under 1 second on modern hardware.
- NFR2.2: Diff computation for a 10,000-line file must complete in under 3 seconds.
- NFR2.3: Memory usage must not exceed 5x the size of the largest reconstructed file.

#### NFR3 — Correctness
- NFR3.1: Output of `get` must be byte-identical to the original file content before check-in.
- NFR3.2: Round-trip test: `admin` → edit → `delta` → `get` must produce identical content.
- NFR3.3: All test cases must pass against real `s.` files from UNIX history archives.

#### NFR4 — Error handling
- NFR4.1: Malformed SCCS files must produce a descriptive warning and recover gracefully where possible.
- NFR4.2: File-not-found and permission errors must produce clear user-facing messages.
- NFR4.3: Unexpected `^A` control codes in the body must be handled without crashing.

#### NFR5 — Code quality
- NFR5.1: Public API must be documented with Javadoc.
- NFR5.2: Library (`com.sccs.lib`) must have no third-party dependencies (Picocli and SLF4J are CLI-only).
- NFR5.3: Test coverage must exceed 80% for the library module.

#### NFR6 — CLI UX
- NFR6.1: All commands must support `--help` output generated by Picocli.
- NFR6.2: Exit code 0 for success, non-zero for errors.
- NFR6.3: Error messages must go to stderr; normal output to stdout.

## 2. Use Cases

### Primary Use Cases

#### 1. Initialize a file for version control

**Actor:** User  
**Trigger:** User has a new or existing file they want to track with SCCS.  
**Flow:** User runs the `admin` command to create an `s.<file>` history file in an `SCCS/` directory, optionally providing a descriptive comment.  
**Outcome:** A new SCCS history file is created with the full header format (checksum, delta table, flags) containing the initial revision.  
**FR:** FR1.1, FR1.2, FR1.3

#### 2. Check out a file revision

**Actor:** User  
**Trigger:** User needs to view or work with a specific revision of a tracked file.  
**Flow:** User runs the `get` command with an optional SID. If no SID is given, the most recent delta (by timestamp) is retrieved. The system walks reverse deltas (`^AI`/`^AD`/`^AE` control records) to reconstruct the file content.  
**Outcome:** The reconstructed file is written to disk, byte-identical to the original content before check-in.  
**FR:** FR2.1, FR2.2, FR2.3, FR6.1, FR6.2, FR6.3, NFR3.1

#### 3. Edit-mode checkout with locking intent

**Actor:** User  
**Trigger:** User intends to modify a tracked file and wants advisory locking.  
**Flow:** User runs `get -e` to check out the latest revision. The system records an advisory lock on the file.  
**Outcome:** File is checked out with the edit flag set, signaling that a subsequent `delta` is expected.  
**FR:** FR2.4

#### 4. Submit a new delta

**Actor:** User  
**Trigger:** User has modified a checked-out file and wants to record the changes.  
**Flow:** User runs the `delta` command. The system computes the difference between the modified file and the previous version using an in-house diff algorithm, stores only the change set (not the full file), and records metadata (timestamp, author, SID, comment). The delta table, checksum, and body encoding are updated.  
**Outcome:** A new revision is appended to the SCCS history file.  
**FR:** FR3.1, FR3.2, FR3.3, FR3.4, FR3.5

#### 5. View revision history

**Actor:** User  
**Trigger:** User wants to inspect the change log of a tracked file.  
**Flow:** User runs the `prs` command, optionally filtering by a specific SID or range. The system prints the delta table (SID, date, author, comment) and any flags/metadata stored in the history file.  
**Outcome:** Revision history is printed to stdout.  
**FR:** FR4.1, FR4.2, FR4.3

### Secondary Use Cases

#### 6. Recover from a malformed SCCS file

**Actor:** System / User  
**Trigger:** An `s.` file contains unexpected `^A` control codes or corrupt header data.  
**Flow:** The parser produces a descriptive warning and recovers gracefully where possible, continuing to process valid portions of the file.  
**Outcome:** Partial or full recovery without crashing; user is informed of the issue.  
**FR:** NFR4.1, NFR4.3

#### 7. Round-trip integrity verification

**Actor:** User (or automated test)  
**Trigger:** User or CI wants to verify that a file survives a check-in/check-out cycle intact.  
**Flow:** A file is checked in via `admin`, modified and submitted via `delta`, then retrieved via `get`.  
**Outcome:** The retrieved file is byte-identical to the original.  
**FR:** NFR3.2

#### 8. Cross-platform execution

**Actor:** User  
**Trigger:** User runs the CLI tool on Windows, macOS, or Linux.  
**Flow:** The same compiled artifact is executed on any supported OS with identical behavior. File paths use platform-independent separators.  
**Outcome:** Consistent behavior across platforms.  
**FR:** NFR1.1, NFR1.2

#### 9. Encrypted revision storage

**Actor:** System  
**Trigger:** An SCCS history file has the `y` (encryption) flag set.  
**Flow:** On `delta`, the body is XOR-encrypted before storage. On `get`, the body is XOR-decrypted during reconstruction.  
**Outcome:** File bodies are stored encrypted on disk.  
**FR:** FR5.5

#### 10. Branched SID retrieval and creation

**Actor:** User  
**Trigger:** User wants to work with a revision on a branch (non-trunk SID).  
**Flow:** User specifies a branched SID with `get` or commits a delta that creates a branch. The system handles the non-linear revision graph.  
**Outcome:** Branched revisions are correctly retrieved or created.  
**FR:** FR2.5

## 3. Happy Paths & Broken Paths

### UC1: 3.1 Initialize a file for version control (`admin`)

| Type | Scenario | Notes |
|------|----------|-------|
| **Happy** | Track a new file that does not yet exist on disk | Creates `s.<file>` with initial 1.1 delta |
| **Happy** | Track an existing file | Reads existing content, stores as initial 1.1 delta |
| **Happy** | Provide descriptive comment via `-y` | Comment recorded in delta table |
| **Happy** | Create `SCCS/` directory implicitly when missing | Directory auto-created |
| **Broken** | Target file already has an `s.` history file | Should fail with "already exists" |
| **Broken** | Target path contains invalid characters or max-path-length exceeded | Should produce clear file-system error |
| **Broken** | Target file is empty | Should succeed — empty initial delta is valid |
| **Broken** | Disk full / write-protected during history file creation | Should fail gracefully with OS error |
| **Broken** | Permission denied on parent directory | Should fail with clear permission error |

### UC2: 3.2 Check out a file revision (`get`)

| Type | Scenario | Notes |
|------|----------|-------|
| **Happy** | Get latest revision (no SID specified) | Walks reverse deltas, reconstructs latest |
| **Happy** | Get specific SID (e.g., `1.3`) | Retrieves exact revision |
| **Happy** | Get SID that is trunk (e.g., `1.x`) | Works normally |
| **Happy** | Reconstructed file is byte-identical to original | NFR3.1 verified |
| **Happy** | History file has only 1 delta (initial) | Single reverse-delta walk, immediate result |
| **Broken** | Requested SID does not exist in delta table | Should fail with "SID not found" |
| **Broken** | History file is corrupted (bad checksum) | Should detect and report checksum mismatch |
| **Broken** | History file has cyclic delta references | Walk never terminates; should detect cycle |
| **Broken** | History file missing `^AI`/`^AD`/`^AE` control records for a delta | Should fail with parse error |
| **Broken** | File already checked out writable (no `-e`) | Should warn if output path already writable |
| **Broken** | History file is empty or has no deltas | Should fail with "no deltas in file" |

### UC3: 3.3 Edit-mode checkout with locking intent (`get -e`)

| Type | Scenario | Notes |
|------|----------|-------|
| **Happy** | `get -e` on an unlocked file | File checked out writable, advisory lock set |
| **Happy** | `get -e` on same file after previous `delta` committed | Lock released by delta, new lock acquired |
| **Broken** | `get -e` on a file that is already locked by another user | Should fail with "already locked" |
| **Broken** | `get -e` on a file that is already locked by same user | Should warn but may allow (advisory) |
| **Broken** | `get -e` when file is read-only (permissions) | Should fail with permission error |
| **Broken** | Lock file left from previous crash (stale lock) | Should detect stale lock and optionally auto-remove |

### UC4: 3.4 Submit a new delta (`delta`)

| Type | Scenario | Notes |
|------|----------|-------|
| **Happy** | `delta` on a file checked out with `get -e` | New revision created, SID incremented (e.g., 1.2) |
| **Happy** | File has multiple changes between check-out and delta | Diff computed correctly |
| **Happy** | Provide comment via `-y` | Comment recorded in new delta entry |
| **Happy** | `delta` with no changes (file identical to base) | Should create empty delta or no-op |
| **Broken** | `delta` on a file that was not checked out with `get -e` | Should fail with "not checked out" |
| **Broken** | `delta` on a file that is locked by another user | Should fail with "locked by other user" |
| **Broken** | Checked-out file has been deleted from disk | Should fail with "working file not found" |
| **Broken** | In-house diff produces incorrect result | Leads to corrupted delta — covered by NFR3.2 |
| **Broken** | Disk full while writing new delta to history file | Should fail gracefully; history file left in consistent state |
| **Broken** | Lock file is missing (stale) during delta | Should record delta but warn about lock state |
| **Broken** | Multiple concurrent `delta` calls on same file (race) | Should serialize via file locking or fail second |
| **Broken** | SID sequence overflow (e.g., `1.99999 -> 1.100000`) | Should handle numerically |

### UC5: 3.5 View revision history (`prs`)

| Type | Scenario | Notes |
|------|----------|-------|
| **Happy** | `prs` with no options | Prints full delta table |
| **Happy** | `prs` with specific SID | Prints only that delta record |
| **Happy** | `prs` with SID range (e.g., `-r1.1 -r1.5`) | Prints deltas in that range |
| **Happy** | History file has multiple branches | Prints all deltas with branch SIDs visible |
| **Broken** | Requested SID does not exist | Should fail with "SID not found" |
| **Broken** | History file is corrupted | Should partially print valid deltas, warn about corrupted ones |
| **Broken** | History file has flags but no deltas | Should print flags and show empty delta table |
| **Broken** | Range start > range end | Should produce empty output or warn about invalid range |

### UC6: 3.6 Recover from a malformed SCCS file

| Type | Scenario | Notes |
|------|----------|-------|
| **Happy** | Single `^A` control code corrupted | Parser warns, skips corrupt line, continues |
| **Happy** | Header checksum mismatch | Warns, reparses, or continues if recoverable |
| **Happy** | One delta's body corrupt but header intact | Returns partial data with warning |
| **Broken** | Entire file is binary garbage | Cannot recover; should report "unable to parse" |
| **Broken** | Critical header field missing | Fails with "malformed header" |
| **Broken** | Checksum field itself is corrupt | Should detect recomputed vs stored mismatch |
| **Broken** | `^AI`/`^AD`/`^AE` control records out of order | Parser should detect invalid delta sequencing |
| **Broken** | File is truncated mid-record | Should detect premature EOF and report location |

### UC7: 3.7 Round-trip integrity verification

| Type | Scenario | Notes |
|------|----------|-------|
| **Happy** | Binary file: `admin` → `get -e` → modify → `delta` → `get` | Byte-identical to final version |
| **Happy** | Text file: same cycle | Byte-identical |
| **Happy** | Large file (e.g., 100MB): same cycle | Byte-identical |
| **Happy** | Empty file: same cycle | Byte-identical |
| **Happy** | Multiple deltas in sequence: `admin` → `delta` × N → `get` at each step | Each step retrieves correctly |
| **Broken** | In-house diff produces wrong output on edge-case input | NOT byte-identical — single test failure catches it |
| **Broken** | Line-ending normalization (CRLF vs LF) between platforms | May break byte-identity between Windows and Unix |
| **Broken** | Non-UTF-8 binary content with `^A` byte (0x01) | Must be properly escaped/encoded in body |
| **Broken** | File with trailing newline changes between check-out and delta | Leading/trailing whitespace preserved |

### UC8: 3.8 Cross-platform execution

| Type | Scenario | Notes |
|------|----------|-------|
| **Happy** | `admin` on Windows creates `SCCS\s.file` | Platform path separator |
| **Happy** | `get` on macOS | Correct behavior |
| **Happy** | `delta` on Linux | Correct behavior |
| **Happy** | History file created on Windows, `get` on Linux | Cross-platform `s.` file portability |
| **Broken** | Path with backslashes on Unix | Should use `/` on Unix |
| **Broken** | Unicode filename on Windows vs Linux | Path encoding differences |
| **Broken** | File permissions differ by platform | `get -e` read-only/writable semantics |
| **Broken** | Case-insensitive filesystem (Windows) vs case-sensitive (Linux) | `s.FILE` vs `s.file` collision |

### UC9: 3.9 Encrypted revision storage

| Type | Scenario | Notes |
|------|----------|-------|
| **Happy** | `y` flag set, `delta` stores XOR-encrypted body | Body unreadable without decryption |
| **Happy** | `get` on encrypted history file | Body decrypted, content matches original |
| **Broken** | `y` flag set but body was stored unencrypted (manual edit) | Decrypt produces garbage; should warn |
| **Broken** | `y` flag NOT set but body is XOR-encrypted | Raw binary output; should detect magic |
| **Broken** | Encryption key lost or changed | All `get` operations produce garbage |
| **Broken** | XOR on binary file containing 0x00 bytes | Should not truncate — XOR with 0x00 = identity |

### UC10: 3.10 Branched SID retrieval and creation

| Type | Scenario | Notes |
|------|----------|-------|
| **Happy** | `get -r1.2.1.1` retrieves branch revision | Branch delta walked correctly |
| **Happy** | `delta` on a branch SID creates next branch revision | e.g., `1.2.1.1` → `1.2.1.2` |
| **Happy** | Check out trunk, make delta, then delta creates branch | Auto-branching on edit conflict |
| **Happy** | Interleaved trunk and branch deltas exist in history | Both paths correctly reconstructable |
| **Broken** | Requested branch SID does not exist | Should fail with "SID not found" |
| **Broken** | Branch parent SID does not exist in delta table | Should fail with "parent SID not found" |
| **Broken** | Deeply nested branches (e.g., `1.2.1.3.2.1`) | Walk depth should be bounded or recursive |
| **Broken** | Branch revision graph has a fork (two children from same parent) | Should handle non-linear graph |
| **Broken** | Branch SID with zero sequence number (e.g., `1.2.0.0`) | Invalid SID format — should reject |
